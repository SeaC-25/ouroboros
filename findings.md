## Initial Archive Shape
- Kali-Security-MCP is a large Python/MCP pentest orchestration codebase with `kali_mcp/core`, `agents`, `deep_test_engine`, parsers, event bus, scheduler, result aggregation, checkpoints, AI context, and historical planning/output dumps.
- Eidolon is a Dockerized offensive workstation/environment wrapper with multiple profile Dockerfiles (`base`, `web`, `net`, `pivot`, `wifi`, `mobile`, `ad`, `claude`) and shell gateway helpers under `scripts/`.
- Xalgorix is a Go agent platform with CLI entrypoint, auth/provider layers, sandbox/scope guard, scan context stores, notes/vuln stores, browser/page-agent tooling, proxy support, reporting, and a large embedded skill knowledge corpus.

## Project Notes

### Project A: Kali-Security-MCP-main
- Kali-MCP has an actual `mcp_server.py` entrypoint despite the first truncated file listing hiding it. It registers many MCP tool modules, security profiles, agents, message bus, executor, and optional SSE/stdio transport.
- Kali-MCP execution path: MCP tool call -> `LocalCommandExecutor.execute_tool_with_data()` -> engagement scope/profile gate -> declarative `tool_registry.build_command()` -> `subprocess.run(shell=True)` -> structured output parser -> synchronous in-process `EventBus.emit("tool.result")`.
- It has multiple overlapping orchestration concepts: `PipelineOrchestrator` (stage state machine), `AgentScheduler` (capability/load-based assignment), `AdaptiveParallelEngine` (DAG/resource-aware parallelism), and `HighSpeedExecutor` (queue/cache/rate limiter). This is powerful but fragmented.
- Precision primitives exist but are uneven: parser-level `ParsedResult(confidence,severity,next_steps)`, `ResultAggregator` heuristic extraction/dedupe/correlation, `VulnManager` candidate/verifying/verified lifecycle and blackbox/whitebox cross-validation. Some paths use regex keyword heuristics with fixed confidence.
- Persistent state exists in SQLite under `~/.kali_mcp/` for checkpoints and vulnerabilities; many runtime states remain global dicts in `mcp_server.py`.

### Project B: eidolon-main
- Eidolon's core is the `scripts/gw` Bash orchestrator: strict mode, active engagement state in `~/.config/eidolon/active`, artifacts rooted at `/shared`, fixed subdirectories `{recon,scans,creds,loot,reports,logs}`, and command wrappers for recon/web/fuzz/ad/mobile/wifi/report.
- Eidolon packages capability by scenario through Docker variants: base, web, net, ad/cloud, mobile, wifi, pivot, claude. It optimizes operator setup and repeatability more than result semantics.
- Its data contract is mostly filesystem convention. `gw new` writes `engagement.yml` and creates stable output folders; each pipeline writes raw `.txt`, `.json`, `.pcap`, zipped BloodHound data, reports, etc. Downstream consumption is by path and filename convention, not typed API.
- Error behavior intentionally favors continuation: many tool calls end with `|| true`, so a failed sub-step does not kill the pipeline. That improves late-night workflow continuity but hides partial failure unless logs are inspected.
- Precision is delegated to wrapped tools and manual/AI interpretation. Eidolon has quality gates and report collation, but no native confidence model, dedupe, verification status, or cross-tool adjudication.
- Efficiency bottleneck is mainly external tools and container scope: `gw` is sequential Bash, no task DAG, no shared cache, and no scheduler beyond the operator choosing a variant.

### Project C: xalgorix-main
- Xalgorix documents a Go Web Server + Agent Engine + Tool Layer. It has Web UI, CLI, API, WebSocket telemetry, scan modes, JSON state files, and report/PDF generation.
- Xalgorix execution path: Web/CLI request -> `ScanRequest`/`scanSession` -> per-session `scanctx.ScanContext` -> `agent.Agent` LLM loop -> `tools.Registry.Execute()` -> terminal/browser/reporting/etc. tools -> event stream -> `ScanRecord` persisted as JSON and optional PDF.
- Its best architecture assets are runtime isolation and UX telemetry: per-scan context, WebSocket `WSEvent`, buffered event replay, scan instances, pause/resume, queue state, restart auto-resume, PDF reports, settings UI, and resource-aware admission.
- Precision is enforced at the reporting boundary: `report_vulnerability` rejects missing verification method/proof, applies false-positive patterns, deduplicates by target/endpoint/type, enforces CVSS-to-severity mapping, and marks `Verified` when proof+method exist. It is stricter than Eidolon but still depends heavily on LLM/tool self-reporting.
- Xalgorix has strong resilience controls: per-tool hard timeouts, watchdog process killing, circuit breaker after repeated tool failures, panic-safe cleanup/persistence, path policy, scope guard for local/private targets, and resource leases for heavy tools.
- Documentation has a storage-path drift: README says `~/xalgorix-data/`, while current config/server code defaults to `~/.xalgorix/data/`.

## Cross-Cutting Findings
- The earlier integration-first approach would import too much architecture debt from the three source projects. Kali-MCP's large exposed tool surface creates routing ambiguity and token waste; Eidolon's Bash orchestration is useful as environment philosophy but not as a platform core; Xalgorix's control plane is useful as UX/event inspiration but should not dictate the agent loop.
- Ouroboros should be designed from scratch as a goal-driven automated pentest platform. The source projects are reference material for philosophy, parsers, environment packaging, telemetry, and report UX.
- Tool count must not be exposed as the agent interface. A Tool Compiler should map semantic actions to concrete tools internally.
- Bottom-layer appsec tools now need two separate maturity tracks: catalog/manifest visibility for `nuclei`, `httpx`, `subfinder`, `ffuf`, `katana`, `nmap`, `naabu`, `dnsx`, and adjacent tools; then a later binary/rule-bundle packaging track that proves users no longer need manual host installation.
- Model-authored tools must enter through structured native specs with declared inputs, expected evidence, parser, dependencies, and safety controls. Raw shell scripts or `sh -c` wrappers should remain rejected unless a later command-runner path explicitly applies target boundary, exclusion, isolation, and authorization checks.
- The platform needs a Sisyphus-style loop: goal, hypothesis, plan, attempt, evidence, failure analysis, strategy mutation, next attempt.
- ABC goals are unified as a Goal Stack: Mission Goal, Coverage Goal, Evidence Goal, and Report Goal.
- Product form should be TUI-first rather than WebUI-first: a terminal pentest compiler/IDE with Workspace, Mission Conversation, Attack Graph, Agent Graph, Runtime panels, and a status bar.
- Long-running automation needs visible model telemetry: current model, role, token usage, cost, context window, compaction thresholds, and multi-model role assignment.
- Multi-agent execution needs a Swarm Orchestrator and Agent Graph. Agent outputs synchronize through Event Log and Evidence Graph rather than free-form inter-agent chat.
- Breadth and depth need explicit control through Coverage Matrix, Frontier Queue, Objective Chain, and scoring of candidate paths.
- Tools should mature toward a Native Toolchain Runtime with manifest locks, health checks, parser bindings, offline bundles, and workspace-managed packaging that avoids reliance on ambient host `PATH`.
- The security-operator chat surface should keep common IDE questions local when possible. Commands such as `/status`, `/next`, `/command`, `/artifacts`, `/gates`, `/runs`, `/reports`, `/toolchain`, `/safety`, `/providers`, `/workers`, `/context`, `/actions`, and `/usage` give immediate workspace answers without provider calls, replay mutation, prompt persistence, report path/manifest path/scope path/provider URL/environment-variable-name/worker endpoint/worker label disclosure, or target contact, while normal prompts remain provider-backed and history-filtered.
- Provider-backed AI dialog prompts should teach the model the safe action language without exposing the tool layer. The context can include declared compiler semantic-action IDs, the canonical `semantic_action:<action>` marker format, preview-only mode, and operator-review requirement, but must not include tool names, command arrays, manifest paths, target values, provider URLs, model names, API-key environment names, workspace paths, local command transcript text, secrets, or bearer tokens.
- Operators should be able to inspect that safe action language without asking a provider. `/actions`, `/semantic-actions`, and `/action-list` are local-only chat commands that return declared semantic-action IDs and marker format with `stored=false`, while avoiding tool-name, command-array, manifest-path, workspace-path, provider, secret, artifact-write, worker-dispatch, tool-execution, and target-contact exposure.
- Final completion evidence needs a read-only operator status surface separate from the audit script itself. `ouro completion-status <audit-log-dir>` now inspects the three-file completion evidence set, rejects symlinked evidence paths, verifies fixed v1 schemas, verifies result/manifest/sidecar path fields are absolute and point back to the fixed files being inspected, verifies that `remaining_manual_step` stays on `claim_100_after_real_operator_evidence_review`, recomputes result/manifest SHA-256 values, rejects ready status when recorded manifest/digest-sidecar values do not match actual file bytes, reports ready/missing/partial/schema-mismatch/manual-step-mismatch/relative-link/link-mismatch/digest-mismatch posture and digest values, and keeps `claim_100_ready=false` so the CLI cannot be mistaken for final human acceptance.
- Final completion evidence also needs an explicit operator-owned acceptance artifact, not an implicit 100% inference from the audit script. `ouro completion-accept <audit-log-dir> --reviewed-by <operator> --accept-real-evidence` now writes `completion-final-acceptance.txt` only after completion evidence is `ready-for-final-review`; `completion-status` verifies that optional artifact by schema, absolute paths, SHA-256 bindings to the current result/manifest/digest sidecar and manifest-linked production summary/attestation/policy files, `real_operator_evidence_reviewed=true`, `fixture_evidence_accepted=false`, and fixture-marker rejection before reporting `claim_100_ready=true`. This artifact is local mutable review evidence, not a signature or append-only ledger, and fixture evidence must still be rejected.
- Final acceptance must bind the evidence bytes that the audit manifest recorded, not just whatever linked files contain later. The acceptance path now rejects changed production summary, attestation, or policy files when their current SHA-256 differs from `production_summary_sha256`, `attestation_sha256`, or `policy_sha256` in the completion manifest, and it reads the attestation body for fixture markers such as `reviewed_by=final-evidence-fixture`, non-`operator_owned` `production_evidence`, or non-false `fixture_evidence_allowed`. The audit log directory must be absolute before `completion-accept` writes anything, avoiding a relative-path acceptance that later fails its own status verification.
- Final acceptance paths are evidence too, not just file lookup conveniences. `completion-status` and `completion-accept` now reject audit log directories, completion evidence files, manifest-linked production summary/attestation/policy paths, final-acceptance linked paths, and final acceptance output paths that pass through existing symlink path components or use non-canonical `.`/`..` spellings, even when the final path leaf is a regular file. This keeps the path spelling reviewed by the operator aligned with the bytes parsed, compared, and hashed by the CLI.
- Final acceptance publication needs a second path check after temporary-file creation. `completion-accept` now revalidates the completion audit log directory and final acceptance output path immediately after closing the same-directory temporary file and before `rename`, so a path replacement between the earlier review checks and publication fails before a local mutable acceptance artifact can be published through a replaced log directory. This is still local filesystem hardening, not a signature or append-only guarantee.

## Additional Cross-Cutting Learnings
- BreachWeave's Manager/Solver/Observer maps cleanly onto Ouroboros's Swarm Orchestrator, Agent Workers, and Context/Observer Agent. The useful idea is not fixed roles for all domains, but explicit separation between global control, path execution, and runtime supervision.
- Cairn's Fact/Intent/Hint model is a strong candidate for refining Ouroboros's Evidence Graph: Facts are confirmed statements, Intents are open exploration edges, and Hints are graph-external steering inputs.
- Cairn's Dispatcher design reinforces that Agent workers should not directly mutate shared protocol state. Ouroboros should keep Swarm Orchestrator as the sole writer to core state, with agents returning structured outputs.
- Cairn's `bootstrap/reason/explore` task trinity is a compact alternative to over-specific agent roles: bootstrap tries a direct solve, reason decides completion or next intent, explore executes one intent.
- aide's pattern YAMLs validate modeling strategies as configurable graphs: RalphLoop for persistence, Explore-Plan-Execute for deliberate planning, Ant Colony for parallel path search and reusable trails.
- aide's CTF overlay argues for hypothesis-first operation: form likely exploit paths before broad scanning, budget early attempts, then escalate to heavier enumeration only when signals justify it.
- BreachWeave's runtime tracks `main`, `subagent`, and `observer` threads for a solver, and its timeline separates `challenge`, `solver`, `observer`, `board`, and `submission` lanes. Ouroboros's TUI should use similar lane separation for Agent Graph/Timeline clarity.
- BreachWeave's TUI already displays phase, model, input/output token totals, and cost. Ouroboros should extend this to context-window health and multi-agent aggregated cost.
- BreachWeave injects solver binaries into Docker worker containers and stores per-solver workspace/session/startup snapshots. Ouroboros's Native Toolchain Runtime should similarly make worker startup reproducible and inspectable.
- Cairn's conclude fallback after timeout/parse failure is important: failed long-running attempts may still contain useful facts, so Ouroboros should have Attempt Conclude/Summarize fallback before discarding work.
- aide's nuclei template tool shows a useful pattern for native corpus tools: expose semantic corpus search/read capability while keeping corpus paths and fallback roots inside the runtime.
- Native corpus hits now return content-addressed artifact refs plus snippets, and corpus path handling must reject any `..` segment rather than relying on path cleaning alone.
- Tool Compiler routing is now capability-based: agents request semantic actions, manifests provide capabilities, and manifest names are not used as hard-coded tool selectors.
- Parser Binding now treats parser failure as recoverable Sisyphus input: successful JSON parser specs become Blackboard Facts and parser/fact events; failed parsing calls Conclude Fallback so partial transcripts can still produce attempt summaries and reusable leads.
- TUI shell minimum viewport is `80x9` for the first three-column layout; the status bar needs compact rendering to preserve model, context, agents, tool health, and cost on medium-width terminals.
- Workspace Panel uses a canonical pentest workspace order before sorting unknown entries, and selection state is path-based so later keyboard navigation can update focus without coupling to row indices.
- The TUI center panel now has two explicit modes: Mission Conversation for global mission state and Agent Workbench for focused agent state, with `Esc` returning focus to the mission conversation.
- TUI Graph Stack now keeps Attack Graph, Agent Graph, and Inspector as one right-column unit; Inspector derives details from the current graph selection so node focus and detail rendering stay synchronized.
- Runtime Tabs keep Node Inspector as the default right-bottom tab and wrap tab headers across rows, which avoids losing tab names in narrow graph-column widths.
- Domain Pack SDK now makes packs declare semantic capabilities, initial hypotheses, coverage dimensions, parser specs, and strategy patterns; packs should reject incompatible target kinds through `InitialHypotheses`.
- Web/API Pack starts URL targets with breadth-first hypotheses: discover the initial surface, enumerate routes, map auth states, then generate parameter/authorization candidates.
- Infra/Internal Pack starts parseable CIDR targets with host discovery, service enumeration, identity mapping, and internal path hypothesis generation.
- CTF/Lab Pack starts challenge targets with exactly three hypothesis-first moves before broad enumeration: classify the challenge, analyze provided artifacts, and generate fast solve hypotheses.
- Replay Store now builds a deterministic run snapshot from event log events: Blackboard state, Evidence Graph, timeline lanes, model usage, agent state, and TUI status are all derived from the replayed event payloads.
- Replay projection keeps `internal/eventlog` independent from `swarm` and `tui` to avoid package cycles; `internal/tui` consumes the generic replay snapshot for UI state.
- Report Projection now turns an Evidence Graph into Markdown sections for verified findings, attack paths, evidence references, exhausted areas, and next-run suggestions.
- Report paths are reconstructed from `derived_from` and `requires` edges, which makes the report explain how target facts and hypothesis/intents led to a verified finding.
- Production Core Bring-Up now has a deterministic offline run path: workspace-local provider config, toolchain manifests, domain-pack initial hypotheses, SQLite event log, replay projection, TUI status projection, and Markdown report generation are connected without network or live target execution.
- Closed-loop planner preview now connects the run event log to Sisyphus decision visibility, a concrete compile-review artifact, a metadata-only model usage accounting preview, and an explicit opt-in provider generation gate without adding autonomous execution. After first-pass tool execution, `ouro run` rebuilds a replay snapshot, calls `sisyphus.Engine.Step`, reads the selected intent action, creates a dry-run metadata-only compile preview review plus current selection marker, and persists stage/agent/planner-review/hint/suggestion events before report projection so the next operator-reviewed plan appears in replay, the TUI Attack Graph, workspace-bound TUI Toolchain Health, and Markdown `Next-Run Suggestions`. The selected review now has both a direct explicit CLI/app execution gate and a separate dry-run execution dispatch artifact that can be executed through `execute-compile-preview-review-execution-dispatch --execute`; dispatch execution reuses strict safety authorization, rejects stale review summaries, and links execution audits through `dispatch_path`. Workspace-bound TUI Toolchain Health can now create dry-run metadata-only dispatch artifacts from current review artifacts through double-confirm `x`, then execute those dispatch artifacts through another double-confirm `x` using the same app gate with `actor=tui` and selecting the resulting audit rows. The planner stage also writes one metadata-only `model_usage_preview` replay event projected into replay/TUI/report state with zero token/cost counters and no manual ledger write.
- Run-integrated provider generation now enters through an explicit planner gate, not default `ouro run`. `--provider-generate` flags and matching `RunOptions` are the operator opt-in boundary for one closed-loop planner generation call. Replay and optional ledger records persist provider/model identity, operation/stage, text digest, bounded short preview, token usage, optional estimated cost, budget status, and ledger write metadata only. Budget enforcement fails closed before optional metadata-only ledger writes or successful replay `model_generation` metadata. The gate does not persist prompts or provider response text verbatim, execute provider-suggested tool calls, run autonomous multi-round planning, route/fail over providers, stream output, dispatch workers, execute another tool round, or contact scoped targets. The remaining loop gap is true autonomous multi-round model-mediated planning, model-mediated tool-call control, provider routing/failover, and production-grade model runtime policy, not the basic run-integrated generation/accounting surface.
- Direct AI usability requires the configured `openai_compatible` provider to be the first enabled provider. Fresh workspaces start with enabled `offline`, so a CLI provider configuration command must upsert the real provider ahead of preserved defaults and disable only the default offline provider when the real provider is enabled; otherwise the TUI AI dialog and manual `provider generate` can still hit the offline adapter after configuration. API keys should remain environment-only: configuration UX should accept `api_key_env`, never an API key value, and should not read or print the environment variable value during configuration.
- Workspace `toolchain/` now carries local manifest copies, and the CTF manifest capability was aligned to `ctf.fast_hypothesis` to match the CTF/Lab domain pack.
- Build and distribution now expose stable local entrypoints: `make test`, `make build`, `make release`, `make doctor`, and `make doctor-strict`. `scripts/build.sh` produces `bin/ouro`; `scripts/release.sh` writes a versioned local tarball plus `SHA256SUMS`; `scripts/install.sh` installs only from a local archive or directory, rejects HTTP(S) sources, and verifies the matching archive checksum when `SHA256SUMS` is present beside the tarball.
- Release-managed payload packaging now has a first built-in rule-bundle seed: local release archives include digest-verified `toolchains/managed-bundles/nuclei-templates/`, and the release-managed install path can copy it into a workspace and link `workspace/toolchain/rules/nuclei-templates` without network access. This proves the managed rule-bundle packaging chain but is not the full upstream Nuclei template corpus or binary payload bundling.
- Release-managed bundle discovery now has a read-only inventory command before import: `ouro toolchain release-managed-bundles <release-root> [name]` lists release-side bundles and reports per-bundle blocked digest/path/provenance/update errors without copying into a workspace. Workspace-bound Toolchain Health shows imported workspace-local `managed bundle:` rows with read-only Inspector details, and `ouro toolchain release-managed-status <workspace> <release-root> [name]` now provides the combined release/workspace import-status matrix with `digest_status=verified|blocked`, `import_status=not_imported|imported|linked|conflict|blocked`, and `link_status=missing|linked|conflict|blocked`. Named release-managed status, install-plan, and install commands can take `--expected-sha256 <sha256>` as a separate operator-side payload pin; matches print `expected_sha256_status=matched`, mismatches print or return `expected_sha256_status=mismatch`, block import/link/install before workspace writes, and preserve manifest/payload `digest_status` as its own self-validation result. Optional manifest `provenance:` metadata surfaces as `provenance_status` plus `source_url`, `upstream_version`, `retrieved_at`, and `verified_by` values in app/CLI/TUI rows; optional manifest `update:` metadata surfaces as `update_status=unknown|current|update_available|blocked` plus latest version/digest, checked time, and message values. Invalid provenance or update metadata blocks read/status before workspace writes, but both are only offline review clues and do not become trust roots, downloaders, signatures, remote sync policies, expected pins, status-source policies, or workspace conflict criteria. A workspace-local `toolchain/release-managed-status-source.json` marker, written through `release-managed-status-source-set --set` and cleared through `release-managed-status-source-clear --clear`, gives the TUI a stable release-root input so Toolchain Health can render the source, summary, and per-bundle `release managed status:` rows with full paths in read-only Inspector details. The marker can now persist one local `--pin-bundle <name> --expected-sha256 <sha256>` policy: flags are required together, digests are normalized, missing pinned bundles fail marker writes, matches preserve normal counts, and mismatches persist `expected_sha256_status=mismatch` while blocking only the pinned bundle in read-only source/TUI projections. The marker still does not persist provenance or update policy, and the matrix/TUI projection remain only operator visibility layers: they do not copy bundles, create links, run payloads, execute health probes, call package managers, download content, contact providers, dispatch workers, contact endpoints/targets, or mutate replay/report state.
- Managed bundle signatures are now an offline consistency check, not a remote trust system. Optional manifest `signature:` metadata uses Ed25519 to verify a fixed message containing bundle `name`, `kind`, `version`, and `payload_sha256`; matching records surface as `signature_status=verified` plus algorithm, key id, signed time, and signer metadata, missing records surface as `signature_status=missing`, and invalid records surface as `signature_status=blocked` in inventory/status list paths or fail strict read/install APIs before workspace copy/link writes. CLI output covers `managed-bundles`, `release-managed-bundles`, `release-managed-status`, managed/release install-plan, and managed/release install results; workspace-bound TUI rows and RuntimeAction/Inspector details expose the same metadata. The embedded public key and signer fields remain review metadata rather than a trust anchor, keyserver, downloader, update channel, expected digest pin, status-source policy, or remote provenance proof. `release-managed-status-source-set --set` may still write the explicit release-root marker because that marker is only a local TUI input; per-bundle status rows then show blocked signatures and import/link remain blocked.
- Local managed payload import is now the workspace-side authoring bridge for operator-supplied binaries and rule bundles. `ouro toolchain managed-bundle-import <workspace> <name> <payload> --kind binary|rule_bundle --version <version> --source <source> [--expected-sha256 <sha256>] --import` copies only a local regular file for `binary` or a non-empty local directory for `rule_bundle`, computes either streaming file SHA-256 or canonical record v1 directory SHA-256, rejects source paths replaced by symlinks or different inodes after inspection through `file.Stat()` / `os.SameFile` revalidation, optionally rejects invalid or mismatched operator-declared expected digests before any workspace bundle write, normalizes copied rule-bundle file permissions to `0644`, writes `bundle.yaml` through same-directory random temporary files without overwriting pre-existing fixed `.tmp` paths, and reuses `ReadManagedToolBundle` for manifest/digest/provenance/update readback. Rule-bundle directory records include a fixed format prefix plus sorted slash-normalized relative paths, path lengths, file sizes, and per-file content SHA-256 values; release-managed status now exposes that scope as `directory_canonical_records`. It deliberately stops before final `toolchain/bin` or `toolchain/rules` link creation, payload execution, network fetches, archive unpacking, package managers, health probes, pack manifest edits, release-managed source marker writes, replay/report mutation, provider/worker contact, or target contact. Production third-party binary corpus packaging, broader remote trust policy, and richer rule-corpus provenance remain separate follow-ups.
