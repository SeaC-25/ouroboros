## Initial Archive Shape
- Kali-Security-MCP is a large Python/MCP pentest orchestration codebase with `kali_mcp/core`, `agents`, `deep_test_engine`, parsers, event bus, scheduler, result aggregation, checkpoints, AI context, and historical planning/output dumps.
- Eidolon is a Dockerized offensive workstation/environment wrapper with multiple profile Dockerfiles (`base`, `web`, `net`, `pivot`, `wifi`, `mobile`, `ad`, `claude`) and shell gateway helpers under `scripts/`.
- Xalgorix is a Go agent platform with CLI entrypoint, auth/provider layers, sandbox/scope guard, scan context stores, notes/vuln stores, browser/page-agent tooling, proxy support, reporting, and a large embedded skill knowledge corpus.

## Project Notes

### Project A: Kali-Security-MCP-main
- Kali-MCP has an actual `mcp_server.py` entrypoint despite the first truncated file listing hiding it. It registers many MCP tool modules, security profiles, agents, message bus, executor, and optional SSE/stdio transport.
- Kali-MCP execution path: MCP tool call -> `LocalCommandExecutor.execute_tool_with_data()` -> engagement scope/profile gate -> declarative `tool_registry.build_command()` -> `subprocess.run(shell=True)` -> structured output parser -> synchronous in-process `EventBus.emit("tool.result")`.
- It has multiple overlapping orchestration concepts: `PipelineOrchestrator` (stage state machine), `AgentScheduler` (capability/load-based assignment), `AdaptiveParallelEngine` (DAG/resource-aware parallelism), and `HighSpeedExecutor` (queue/cache/rate limiter). This is powerful but fragmented.
- Precision primitives exist but are uneven: parser-level `ParsedResult(confidence,severity,next_steps)`, `ResultAggregator` heuristic extraction/dedupe/correlation, `VulnManager` candidate/verifying/verified lifecycle and blackbox/whitebox cross-validation. Some paths use regex keyword heuristics with fixed confidence.
- Persistent state exists in SQLite under `~/.kali_mcp/` for checkpoints and vulnerabilities; many runtime states remain global dicts in `mcp_server.py`.

### Project B: eidolon-main
- Eidolon's core is the `scripts/gw` Bash orchestrator: strict mode, active engagement state in `~/.config/eidolon/active`, artifacts rooted at `/shared`, fixed subdirectories `{recon,scans,creds,loot,reports,logs}`, and command wrappers for recon/web/fuzz/ad/mobile/wifi/report.
- Eidolon packages capability by scenario through Docker variants: base, web, net, ad/cloud, mobile, wifi, pivot, claude. It optimizes operator setup and repeatability more than result semantics.
- Its data contract is mostly filesystem convention. `gw new` writes `engagement.yml` and creates stable output folders; each pipeline writes raw `.txt`, `.json`, `.pcap`, zipped BloodHound data, reports, etc. Downstream consumption is by path and filename convention, not typed API.
- Error behavior intentionally favors continuation: many tool calls end with `|| true`, so a failed sub-step does not kill the pipeline. That improves late-night workflow continuity but hides partial failure unless logs are inspected.
- Precision is delegated to wrapped tools and manual/AI interpretation. Eidolon has quality gates and report collation, but no native confidence model, dedupe, verification status, or cross-tool adjudication.
- Efficiency bottleneck is mainly external tools and container scope: `gw` is sequential Bash, no task DAG, no shared cache, and no scheduler beyond the operator choosing a variant.

### Project C: xalgorix-main
- Xalgorix documents a Go Web Server + Agent Engine + Tool Layer. It has Web UI, CLI, API, WebSocket telemetry, scan modes, JSON state files, and report/PDF generation.
- Xalgorix execution path: Web/CLI request -> `ScanRequest`/`scanSession` -> per-session `scanctx.ScanContext` -> `agent.Agent` LLM loop -> `tools.Registry.Execute()` -> terminal/browser/reporting/etc. tools -> event stream -> `ScanRecord` persisted as JSON and optional PDF.
- Its best architecture assets are runtime isolation and UX telemetry: per-scan context, WebSocket `WSEvent`, buffered event replay, scan instances, pause/resume, queue state, restart auto-resume, PDF reports, settings UI, and resource-aware admission.
- Precision is enforced at the reporting boundary: `report_vulnerability` rejects missing verification method/proof, applies false-positive patterns, deduplicates by target/endpoint/type, enforces CVSS-to-severity mapping, and marks `Verified` when proof+method exist. It is stricter than Eidolon but still depends heavily on LLM/tool self-reporting.
- Xalgorix has strong resilience controls: per-tool hard timeouts, watchdog process killing, circuit breaker after repeated tool failures, panic-safe cleanup/persistence, path policy, scope guard for local/private targets, and resource leases for heavy tools.
- Documentation has a storage-path drift: README says `~/xalgorix-data/`, while current config/server code defaults to `~/.xalgorix/data/`.

## Cross-Cutting Findings
- The earlier integration-first approach would import too much architecture debt from the three source projects. Kali-MCP's large exposed tool surface creates routing ambiguity and token waste; Eidolon's Bash orchestration is useful as environment philosophy but not as a platform core; Xalgorix's control plane is useful as UX/event inspiration but should not dictate the agent loop.
- Ouroboros should be designed from scratch as a goal-driven automated pentest platform. The source projects are reference material for philosophy, parsers, environment packaging, telemetry, and report UX.
- Tool count must not be exposed as the agent interface. A Tool Compiler should map semantic actions to concrete tools internally.
- Bottom-layer appsec tools now need two separate maturity tracks: catalog/manifest visibility for `nuclei`, `httpx`, `subfinder`, `ffuf`, `katana`, `nmap`, `naabu`, `dnsx`, and adjacent tools; then a later binary/rule-bundle packaging track that proves users no longer need manual host installation.
- Model-authored tools must enter through structured native specs with declared inputs, expected evidence, parser, dependencies, and safety controls. Raw shell scripts or `sh -c` wrappers should remain rejected unless a later command-runner path explicitly applies target boundary, exclusion, isolation, and authorization checks.
- The platform needs a Sisyphus-style loop: goal, hypothesis, plan, attempt, evidence, failure analysis, strategy mutation, next attempt.
- ABC goals are unified as a Goal Stack: Mission Goal, Coverage Goal, Evidence Goal, and Report Goal.
- Product form should be TUI-first rather than WebUI-first: a terminal pentest compiler/IDE with Workspace, Mission Conversation, Attack Graph, Agent Graph, Runtime panels, and a status bar.
- Long-running automation needs visible model telemetry: current model, role, token usage, cost, context window, compaction thresholds, and multi-model role assignment.
- Multi-agent execution needs a Swarm Orchestrator and Agent Graph. Agent outputs synchronize through Event Log and Evidence Graph rather than free-form inter-agent chat.
- Breadth and depth need explicit control through Coverage Matrix, Frontier Queue, Objective Chain, and scoring of candidate paths.
- Tools should mature toward a Native Toolchain Runtime with manifest locks, health checks, parser bindings, offline bundles, and workspace-managed packaging that avoids reliance on ambient host `PATH`.

## Additional Cross-Cutting Learnings
- BreachWeave's Manager/Solver/Observer maps cleanly onto Ouroboros's Swarm Orchestrator, Agent Workers, and Context/Observer Agent. The useful idea is not fixed roles for all domains, but explicit separation between global control, path execution, and runtime supervision.
- Cairn's Fact/Intent/Hint model is a strong candidate for refining Ouroboros's Evidence Graph: Facts are confirmed statements, Intents are open exploration edges, and Hints are graph-external steering inputs.
- Cairn's Dispatcher design reinforces that Agent workers should not directly mutate shared protocol state. Ouroboros should keep Swarm Orchestrator as the sole writer to core state, with agents returning structured outputs.
- Cairn's `bootstrap/reason/explore` task trinity is a compact alternative to over-specific agent roles: bootstrap tries a direct solve, reason decides completion or next intent, explore executes one intent.
- aide's pattern YAMLs validate modeling strategies as configurable graphs: RalphLoop for persistence, Explore-Plan-Execute for deliberate planning, Ant Colony for parallel path search and reusable trails.
- aide's CTF overlay argues for hypothesis-first operation: form likely exploit paths before broad scanning, budget early attempts, then escalate to heavier enumeration only when signals justify it.
- BreachWeave's runtime tracks `main`, `subagent`, and `observer` threads for a solver, and its timeline separates `challenge`, `solver`, `observer`, `board`, and `submission` lanes. Ouroboros's TUI should use similar lane separation for Agent Graph/Timeline clarity.
- BreachWeave's TUI already displays phase, model, input/output token totals, and cost. Ouroboros should extend this to context-window health and multi-agent aggregated cost.
- BreachWeave injects solver binaries into Docker worker containers and stores per-solver workspace/session/startup snapshots. Ouroboros's Native Toolchain Runtime should similarly make worker startup reproducible and inspectable.
- Cairn's conclude fallback after timeout/parse failure is important: failed long-running attempts may still contain useful facts, so Ouroboros should have Attempt Conclude/Summarize fallback before discarding work.
- aide's nuclei template tool shows a useful pattern for native corpus tools: expose semantic corpus search/read capability while keeping corpus paths and fallback roots inside the runtime.
- Native corpus hits now return content-addressed artifact refs plus snippets, and corpus path handling must reject any `..` segment rather than relying on path cleaning alone.
- Tool Compiler routing is now capability-based: agents request semantic actions, manifests provide capabilities, and manifest names are not used as hard-coded tool selectors.
- Parser Binding now treats parser failure as recoverable Sisyphus input: successful JSON parser specs become Blackboard Facts and parser/fact events; failed parsing calls Conclude Fallback so partial transcripts can still produce attempt summaries and reusable leads.
- TUI shell minimum viewport is `80x9` for the first three-column layout; the status bar needs compact rendering to preserve model, context, agents, tool health, and cost on medium-width terminals.
- Workspace Panel uses a canonical pentest workspace order before sorting unknown entries, and selection state is path-based so later keyboard navigation can update focus without coupling to row indices.
- The TUI center panel now has two explicit modes: Mission Conversation for global mission state and Agent Workbench for focused agent state, with `Esc` returning focus to the mission conversation.
- TUI Graph Stack now keeps Attack Graph, Agent Graph, and Inspector as one right-column unit; Inspector derives details from the current graph selection so node focus and detail rendering stay synchronized.
- Runtime Tabs keep Node Inspector as the default right-bottom tab and wrap tab headers across rows, which avoids losing tab names in narrow graph-column widths.
- Domain Pack SDK now makes packs declare semantic capabilities, initial hypotheses, coverage dimensions, parser specs, and strategy patterns; packs should reject incompatible target kinds through `InitialHypotheses`.
- Web/API Pack starts URL targets with breadth-first hypotheses: discover the initial surface, enumerate routes, map auth states, then generate parameter/authorization candidates.
- Infra/Internal Pack starts parseable CIDR targets with host discovery, service enumeration, identity mapping, and internal path hypothesis generation.
- CTF/Lab Pack starts challenge targets with exactly three hypothesis-first moves before broad enumeration: classify the challenge, analyze provided artifacts, and generate fast solve hypotheses.
- Replay Store now builds a deterministic run snapshot from event log events: Blackboard state, Evidence Graph, timeline lanes, model usage, agent state, and TUI status are all derived from the replayed event payloads.
- Replay projection keeps `internal/eventlog` independent from `swarm` and `tui` to avoid package cycles; `internal/tui` consumes the generic replay snapshot for UI state.
- Report Projection now turns an Evidence Graph into Markdown sections for verified findings, attack paths, evidence references, exhausted areas, and next-run suggestions.
- Report paths are reconstructed from `derived_from` and `requires` edges, which makes the report explain how target facts and hypothesis/intents led to a verified finding.
- Production Core Bring-Up now has a deterministic offline run path: workspace-local provider config, toolchain manifests, domain-pack initial hypotheses, SQLite event log, replay projection, TUI status projection, and Markdown report generation are connected without network or live target execution.
- Closed-loop planner preview now connects the run event log to Sisyphus decision visibility and a concrete compile-review artifact without adding autonomous execution. After first-pass tool execution, `ouro run` rebuilds a replay snapshot, calls `sisyphus.Engine.Step`, reads the selected intent action, creates a dry-run metadata-only compile preview review plus current selection marker, and persists stage/agent/planner-review/hint/suggestion events before report projection so the next operator-reviewed plan appears in replay, the TUI Attack Graph, workspace-bound TUI Toolchain Health, and Markdown `Next-Run Suggestions`. The remaining loop gap is executing that planner-selected compile review under an explicit operator gate.
- Workspace `toolchain/` now carries local manifest copies, and the CTF manifest capability was aligned to `ctf.fast_hypothesis` to match the CTF/Lab domain pack.
- Build and distribution now expose stable local entrypoints: `make test`, `make build`, `make release`, `make doctor`, and `make doctor-strict`. `scripts/build.sh` produces `bin/ouro`; `scripts/release.sh` writes a versioned local tarball plus `SHA256SUMS`; `scripts/install.sh` installs only from a local archive or directory, rejects HTTP(S) sources, and verifies the matching archive checksum when `SHA256SUMS` is present beside the tarball.
- Release-managed payload packaging now has a first built-in rule-bundle seed: local release archives include digest-verified `toolchains/managed-bundles/nuclei-templates/`, and the release-managed install path can copy it into a workspace and link `workspace/toolchain/rules/nuclei-templates` without network access. This proves the managed rule-bundle packaging chain but is not the full upstream Nuclei template corpus or binary payload bundling.
- Developer documentation now maps extension points for domain packs, tool manifests, strategy patterns, and TUI panels.
- `ouro replay <workspace> <run-id>` now reads the workspace SQLite event log and rebuilds replay snapshot state into a textual summary with event count, model status, tool health, timeline lane counts, and report path. `--format json` exports the same replay state as one structured document with timeline payloads, `--format ndjson` emits one timeline event per line for external analysis tools, and `--format html` emits a self-contained HTML/canvas timeline using the same replay export data. Alternate formats are read-only and incompatible with TUI launch flags. `ouro replay-workbench <workspace> <run-id>` serves the same export data through a local read-only HTTP workbench with HTML, primary JSON, multi-run comparison JSON, primary NDJSON, and session-state GET endpoints plus bounded `--max-requests`; repeatable `--compare-run` IDs are loaded as additional replay exports and rendered through `window.OURO_REPLAYS` with a run selector. JSON/NDJSON workbench endpoints support `?lane=` and `?q=` filtering, while the HTML adds local lane/search filtering over the embedded replay data. `GET /api/session` and `window.OURO_REPLAY_SESSION` expose the selected run, filter state, run IDs, and reusable endpoint URLs, and the HTML updates the URL query string as operators switch run/lane/search state. It rejects mutation methods and does not invoke run, dispatch, transport, worker-control, or artifact mutation paths.
- Hosted replay graph projection should remain a replay-only view. The workbench now exposes primary and comparison Evidence Graph JSON through `GET /api/graph` and `GET /api/graphs`, emits primary graph NDJSON through `GET /api/graph.ndjson`, advertises those paths in session state, and renders embedded graph data through `window.OURO_REPLAY_GRAPHS` plus a local canvas/list. Graph exports include stable edge IDs, node/edge type count summaries, and selected focus metadata; `?q=` filters node and edge metadata, `?node=<id>` focuses the selected node plus one-hop incident edges, and `?edge=<id>` focuses one edge plus its endpoint nodes. NDJSON summary lines carry the same focus metadata, and the browser keeps node/edge focus in URL/session state while rendering a read-only selected detail panel. This is still read-only over replay snapshots and does not create collaborative sessions, dispatch work, transport requests, worker controls, or artifact mutations.
- `ouro toolchain list/health <workspace>` now inspects workspace-local toolchain manifests and built-in readiness, so toolchain state is visible outside `doctor`.
- `ouro run --tui` and `ouro replay --tui` now print deterministic non-interactive TUI snapshots from the replay projection, so CLI automation exposes the same Workspace, Mission Conversation, Attack Graph, Runtime Tabs, and status-bar model state as the TUI model.
- `ouro run --interactive` and `ouro replay --interactive` now launch Bubble Tea from the same replay-derived model used by snapshots; run-side live snapshot streaming and replay-side timeline cursor setup both reuse the event-log replay projection.
- `RunWorkspaceWithOptions` now exposes persisted event and incremental replay snapshot observers; `tui.ReplaySnapshotMsg` lets the Bubble Tea model apply those snapshots through `Update`, creating the foundation for live run streaming without introducing a second UI projection path.
- `ouro run --interactive` now consumes `RunWorkspaceWithOptions.OnSnapshot` directly and sends replay snapshots into the active TUI session, so the interactive run path is wired for live updates even though the current offline run completes quickly.
- Interactive run now has the first operator control path: the TUI `c` key uses a double-confirm runtime cancel flow, the CLI wires that request to the run context cancellation function, and Agent Runtime rows retain cancel-request feedback.
- Interactive run now has first-pass pause/resume controls: the TUI `p` key toggles a runtime requester, the CLI wires it to `RunPauseController`, and queued workers persist `wait_reason: run_paused` until resumed. This is scheduler admission pause, not process suspension.
- `tui.ReplayTimelineMsg` now loads persisted replay events into the TUI model with an event cursor; left/right key handling rebuilds deterministic intermediate snapshots, and Timeline Lanes exposes the cursor position.
- `ReplayWorkspace` and replay interactive launch now use full replay-event-backed TUI models, so timeline stepping is available from the app and CLI paths instead of only in isolated TUI tests.
- Replay Timeline Lanes now focuses automatically in replay cursor mode and displays lane-count bars, current event id/type/lane, prev/current/next event context, and left/right plus home/end key hints, making terminal-native event replay controls visible to the operator without adding any execution path.
- Replay snapshots now retain structured Toolchain Health details, and the TUI Toolchain Health tab renders pack dependency state, source, digest, and failure messages from replayed toolchain events.
- The production run path now emits deterministic stage attempt events for workspace bootstrap, toolchain health, hypothesis seeding, and report projection; this is the first step from one-shot offline event generation toward an observable staged runtime.
- Report projection now participates in live event/snapshot streaming: default runs use `report-projection:started` around report-ready replay metadata and Markdown projection, while `report-projection:completed` is the final durable event in the current deterministic run path. The synchronous projection is now closeable through `RunOptions.DeferReportProjection` / `ouro run --defer-report-projection`, which emits `report-projection:skipped` with reason `deferred`, writes no Markdown, and emits no `report_ready`. `ProjectRunReport` / `ouro report-project <workspace> <run-id> --write` is the explicit out-of-band projection gate for deferred runs; dry-run is metadata-only, write mode replays existing evidence, writes only under `workspace/reports/`, appends `report_ready` only after Markdown write success, and records the report stage without workspace doctor/container-runtime checks, tool execution, worker dispatch, endpoint/target contact, result submission, acknowledgement, lease mutation, or daemon-control application.
- Report projection dispatch artifacts should stay as review input until they cross the separate explicit execution gate. `CreateReportProjectionDispatch` and `ouro report-project-dispatch` persist only dry-run metadata under `workspace/reports/report-projection-dispatches/`, including replay event count and replay digest, and the list/read/TUI dispatch surfaces inspect that JSON without projecting the report. The artifact itself must not write Markdown, append `report_ready`, start or complete `report-projection`, call doctor/container-runtime checks, execute tools, dispatch workers, contact endpoints or targets, submit results, acknowledge requests, mutate leases, or apply daemon controls. `ExecuteReportProjectionDispatch` and `ouro execute-report-project-dispatch --execute` are the deliberately designed execution boundary: they require the execute flag before writes, reject symlinked dispatch files/directories and nested artifact paths, revalidate version/status/mode, the computed report path, replay event count, and replay digest captured by the dry-run artifact, pass the same expected count/digest into the safe report projection writer before the first projection event append, and write audit JSON under `workspace/reports/report-projection-dispatch-executions/`. Failed report writes refresh replay/report state before writing the failed audit, so audit event counts and `written` metadata do not hide partial side effects. Treating stale dispatches, same-count replay mutations, and already projected runs as invalid before writes prevents repeated execution from creating second failed audits. Execution review annotations are a separate metadata layer: `accepted`, `deferred`, and `rejected` decisions can document operator judgment, while `false-positive` should remain rejected as a decision value so false-positive state is recorded explicitly as `rejected` plus reason metadata. A current report must be a closeable marker at `workspace/reports/report-projection-selection.json`, not a latest-file convention; selecting requires an accepted completed written execution audit with safe report path, and clearing rewrites the marker to `status=cleared` without deleting audit context. TUI Timeline Lanes should show dispatch/execution artifacts, annotations, review rows, and current/cleared marker rows; it may use double-confirm `x` to execute only dry-run metadata-only dispatch artifacts by calling `ExecuteReportProjectionDispatch`, to select the resulting execution audit row, and to metadata-only select/clear the current report marker. Non-dry-run dispatch artifacts should remain read-only, and the TUI dispatch execution path must not run tools, dispatch workers, contact endpoints or targets, submit results, acknowledge requests, mutate leases, or apply daemon controls outside the app report projection gate.
- Operator-facing dry-run labels should distinguish planned report targets from generated reports. CLI dry-run report projection and report dispatch output uses `planned_report`, while `report-project --write` keeps the real `report` label. TUI RuntimeAction details use `PlannedReportPath` / `planned report path` for report-dispatch artifacts so downstream UI code does not treat the path as a worker result artifact.
- Toolchain manifests now support `healthcheck: exec` with structured `health_command` arrays; the default health runner executes probes without a shell, reports missing binaries distinctly, and feeds installed-version output into `ouro toolchain health`.
- The production run path now has its first tool execution boundary: Tool Compiler produces `discover_assets` plan nodes, `RunOptions.ToolRunner` executes them, and durable tool events record execution id/status/action/capability before report projection.
- Manifests can now bind a plan node to a direct local command with `runner: command` and `run_command`; command execution uses an attempt-scoped working directory and records transcript plus attempt path in replayable tool events.
- Command bindings now support explicit scope templates for target, target kind, workspace path, and run id; target templates fail closed when a matching scoped target is not present.
- Command-bound worker processes now run with a constrained environment: `PATH` plus explicit `OURO_*` context, avoiding inheritance of host variables such as `HOME`.
- Command-bound workers now support manifest-level `run_timeout_ms`; timed-out commands are recorded as failed durable tool events with the attempt directory and timeout transcript, and report projection is skipped for that failed run.
- Replay projection now surfaces failed tool executions as `ToolHealth=failed`; failed runs remain replayable but no longer fabricate report paths, so CLI replay reports `not-generated` when no report-ready event exists.
- Command-bound target capabilities now require matching scope targets before process execution; unscoped attempts fail closed and persist failed tool events, while non-target probes remain modeled as `healthcheck: exec`.
- Command-bound target execution now enforces `scope.exclusions` before process execution with exact trimmed matching, URL subtree/trailing-slash/default-port normalization, and CIDR/IP containment. `scope.target_policy: disabled` is available as an explicit authorized-workspace escape hatch for false-positive target boundaries, but command templates still require concrete scope values.
- Command execution isolation is now explicit in `scope.yaml`: `execution.isolation: process` keeps the constrained child-process environment and attempt directory, while `execution.isolation: disabled` inherits the host environment and runs from the workspace root for authorized legacy-tool compatibility.
- Command-bound Web/API execution now scans command arguments for URL literals before process execution. Hard-coded `http://` or `https://` arguments must stay within the scoped URL target's scheme, normalized host/default-port, and path boundary unless `scope.target_policy: disabled` is set.
- Command-bound Infra/Internal execution now scans command arguments for IP and CIDR literals before process execution. Hard-coded addresses and prefixes must stay within the scoped CIDR target unless `scope.target_policy: disabled` is set.
- Command-bound CTF/Lab execution now scans command arguments for explicit `challenge:<id>` and `ctf://<id>` literals before process execution. These literals must match the scoped challenge target unless `scope.target_policy: disabled` is set.
- Command-bound execution now has an initial container isolation path. `execution.isolation: container` requires `execution.container.image`, defaults the engine to `docker`, mounts the workspace at `/workspace`, injects container-path `OURO_*` context, and lets the container image resolve the inner tool command.
- Tool-level managed argv builders now participate in container isolation. Process mode still resolves the first argv element to a workspace-managed binary, but container mode skips host binary resolution and passes the registered inner command such as `httpx -json -u <url>` to the configured container image through the existing command runner, preserving scope/exclusion validation, container audit fields, and `OURO_*` context.
- Container isolation now has first-pass sandbox profile controls: network mode, user, read-only rootfs, no-new-privileges, dropped capabilities, memory, CPU, PID limit, seccomp, AppArmor, and tmpfs mounts are rendered as direct engine args and key profile fields are persisted in tool events for replay/audit.
- Workspace doctor now preflights container runtime availability for `execution.isolation: container` by resolving the configured engine and running `image inspect <image>` before run execution.
- Toolchain manifests now support first-pass dependency declarations. Binary dependencies can provide direct health commands and install hints; required missing/failed dependencies downgrade pack health, while optional dependencies remain visible without blocking readiness.
- Container-image dependencies now require SHA-256 digest provenance unless marked optional, and dependency health carries source, digest, and latest-version metadata so update/provenance context is visible before execution.
- Container-image dependency health commands now verify the declared `image_digest` against inspect output, so a local image with the wrong digest downgrades pack health before execution.
- Toolchain dependencies can now carry `install_command` arrays as deterministic install-plan metadata. The health path prints install steps for missing/failed dependencies but intentionally does not execute them.
- Explicit safety bypasses are now visible in workspace readiness checks: `DoctorWorkspace` and `ouro doctor` warn when `scope.target_policy: disabled` or `execution.isolation: disabled` is configured, while preserving those settings as authorized non-blocking escape hatches.
- Toolchain dependencies now support `metadata_source` update metadata. The default provider reads relative fixture files, `file://`, and HTTP(S), compares fetched `latest_version` and `image_digest` with pinned manifest values, and surfaces `update_available`, latest digest, metadata source, and messages through CLI health, replay snapshots, and TUI Toolchain Health rows.
- Tool execution now has first-pass bounded worker concurrency. `execution.tool_concurrency` defaults to `1` for deterministic single-worker behavior and can be raised to execute independent compiled plan nodes concurrently while still persisting replayable tool events before report projection.
- Long-running worker visibility now starts at the event contract: tool workers emit `worker_status: started` events keyed by execution id, final result events keep `execution_status`, replay snapshots merge them, and the TUI Agent Runtime tab can show active/completed/failed worker counts.
- Worker lifecycle visibility now includes queue and scheduler-wait state: each compiled tool plan node emits `worker_status: queued` before dispatch, `worker_status: waiting` with `wait_reason` when local admission blocks, and `worker_status: started` at actual execution start, while final result events keep `execution_status`. Agent Runtime renders queued/waiting/active/completed/failed counts and rows for queued, waiting, or active workers.
- Worker completion visibility now streams final `execution_status` tool events as individual workers finish instead of waiting for the entire concurrent batch. The run observer still receives only durable SQLite-backed events/snapshots, and final error returns remain sorted deterministically after execution settles.
- Scheduler admission now has first-pass per-pack execution policy controls. `execution.pack_policies` can disable a named pack, causing its compiled plan node to emit a durable `execution_status: skipped` event with policy reason while never entering queued/started worker dispatch or runner execution.
- Pack-level container policy inheritance is now wired for admitted tool requests. A pack policy can override container image, network, and resource fields while inheriting unspecified global `execution.container` values such as the engine; merged container fields are persisted in durable tool execution audit payloads.
- Scheduler admission decisions are now first-class replay data. Every compiled plan node emits a durable `kind: scheduler_admission` event before skipped or queued worker events, replay snapshots project those decisions separately from worker lifecycle, and Agent Runtime renders admitted/skipped counts plus policy reasons and container override markers.
- Pack policies now support first-pass resource admission with `max_concurrency`. The in-process scheduler enforces per-pack worker semaphores when global `execution.tool_concurrency` is higher, and admission events/replay/TUI surface the configured pack limit.
- Scheduler admission now also supports local CPU/memory leases. `execution.resource_limits` defines in-process lease pools, pack policies request `cpu_units` and `memory_mb`, and admission events/replay/TUI show request/limit values; this is scheduling admission, not container/cgroup enforcement.
- The concurrent scheduler now acquires pack and CPU/memory leases before global worker slots, so a worker blocked on local resource admission does not consume `execution.tool_concurrency` and cannot starve a compatible unblocked worker.
- The split global/pack/resource limiters were replaced by a single in-process admission limiter. Local global slots, pack limits, CPU units, and memory MB are acquired atomically, so a waiting request does not reserve partial local capacity.
- Worker placement now has a first-pass local audit boundary. `execution.worker_pools` maps manifest packs to named local pools, tool requests default to `worker_id: local`, optional worker-pool `max_concurrency` is enforced by the same atomic local admission limiter, and admission/worker/final execution events carry the worker id and wait reason through replay and TUI Agent Runtime rows. This is not yet remote worker dispatch or a durable cross-process lease system.

This is parser/evidence promotion plus a narrow managed argv and file-output boundary only; production `amass` payload bundling, active enumeration, full source coverage, and broader Infra parser coverage remain separate milestones.
- Parser-side dnsrecon evidence is explicit-domain DNS surface metadata from a managed output file. `dnsrecon_json` facts persist only parser/tool/execution identity, scoped domain, host, record type, value, optional address/CNAME, confidence, and a compact statement; URL, host, and CIDR scopes do not authorize promotion, and out-of-scope/excluded hosts or targets are skipped rather than collapsed. Zone-transfer data, raw records, scanner strings, timestamps, secrets, unsupported record metadata, and unknown keys stay out of durable facts. This is parser/evidence promotion plus a narrow managed argv and file-output boundary only; production `dnsrecon` payload bundling, full DNSRecon mode coverage, zone transfer workflows, and broader Infra parser coverage remain separate milestones.
